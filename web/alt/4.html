The problem

Every agent works in its own chat. The team's context gets lost.

An analysis made with one assistant cannot be reviewed by a colleague's assistant without copying it around. Feedback goes into separate chats, and nobody can see which version is current.

Work spread over chats

  • Each person and each agent has a private copy of the context.
  • Reviews arrive as pasted text, detached from what they are about.
  • Switching to another AI means starting over.
  • Nobody knows who changed what, or which agent did it.

Work in a shared Story

  • People and agents read and write the same Story.
  • A review happens in a fork and comes back as comments or changes.
  • Any MCP client can join; the Story outlives the agent.
  • Every version records which person or agent made it.

How it works

Create, share, connect, review, bring it back.

Create a Story

You or your agent write a document, deck or analysis into a Topic.

Share it

Invite a colleague as a viewer, commenter or editor of that one Story.

They connect their agent

Their own MCP agent signs in with their own account and sees only what was shared.

Review in a fork

The review runs in a fork and returns its findings to the original as comments or a change to accept.

↻ The next round starts from the same Story, whichever agent picks it up.

Security

A shared session never shares your keys.

Organisations kept apart

Every Story, file and cache entry belongs to one organisation, and isolation is tested on every build.

Permissions per Story

Roles are checked on every agent call, in forks too, not only at sign-in.

Your keys stay yours

Your AI API keys are kept in a vault and never reach another agent's context. A session belongs to one person and one Story.

Standard sign-in for agents

Agents connect with OAuth 2.1 as the MCP specification requires: each token is checked to be issued for Sliqtly, and no token is passed on.
